# 03 — LPR Search

**Узкое место пайплайна** (см. build-спеку §13 — реалистичная полнота этого
блока на холодном списке компаний 30–50%, ниже, чем у остальных блоков).
Не пытайся компенсировать это домыслом — прими как ожидаемый результат.

**Вход:** `{company_name, site, hh_url}`.
**Выход:** список персон-кандидатов, прогнанных через `entity_resolve.py`.

## Целевые роли

HRD, директор по персоналу, HRBP, Head of Recruitment, линейные
HR-специалисты.

## Что делать

1. Вызови источники с `category: lpr_search` из `config/sources.md`:

   ```
   python scripts/hh_client.py --url <hh_url> --with-vacancies
   python scripts/site_crawler.py --url <site> --sections team,contacts
   python scripts/habr_client.py --company "<company_name>"
   python scripts/media_search.py --query-set lpr_search --company "<company_name>" --limit 30
   ```

   Вакансии hh.ru часто содержат `contact_person` — это тоже кандидат,
   собери его наравне с остальными.

   **Дополнительно — не вместо, а вместе с `media_search.py` — прогони те
   же шаблоны запросов из `config/query-templates.md` (набор `lpr_search`)
   через собственный инструмент веб-поиска (`web_search`), если он у тебя
   доступен в текущей среде выполнения.** Это не дублирование ради
   подстраховки: на живом прогоне по WMT `media_search.py` (DuckDuckGo с IP
   дата-центра) не нашёл реального, хорошо задокументированного HRD —
   Юлию Образову, HR-тимлида WMT Group, которая упоминается в CNews, РБК,
   Gazeta.ru — и вместо этого выдал непроверяемое имя с сайта, отдающего
   анти-бот заглушку. Один запрос через обычный `web_search` нашёл её
   немедленно и по нормальным источникам. Причина систематическая:
   DuckDuckGo HTML с IP дата-центра — это подтверждённо более слабый
   поисковый бэкенд, чем родной `web_search`, а не разовая случайность (см.
   `config/sources.md` и `SKILL.md`, где это уже отмечено как «ненадёжно»).
   Результаты `web_search` заноси в тот же `candidates.json` наравне с
   остальными источниками (`source: "web_search"`), это не отдельная
   ветка обработки.

   **Также проверь роль-варианты, которых может не быть в
   `config/query-templates.md`** — например «HR-тимлид»/«HR Team Lead»
   встречаются на практике не реже, чем «HRD», но раньше не входили в
   набор `lpr_search` (см. историю правок конфига после разбора кейса WMT).

2. Собери всех найденных кандидатов-персон в один `candidates.json` вида
   `[{name, position, source_url, source, context}, ...]` — по одной записи
   на каждое упоминание, не дедуплицируя вручную (это работа следующего
   шага).

3. **Обязательно прогони через `entity_resolve.py`** — не пропускай этот
   шаг и не полагайся на собственную оценку, кто из кандидатов реальный
   ЛПР, а кто тёзка или случайное упоминание:

   ```
   python scripts/entity_resolve.py --candidates candidates.json \
     --company "<company_name>" --company-domain <домен сайта>
   ```

4. Возьми из вывода `persons[]` — это уже дедуплицированный, атрибутированный
   и оценённый по confidence список. Не переписывай `confidence_suggested`
   вручную (anti-patterns.md: «не выдавать TENTATIVE за CONFIRMED»).

## Если ЛПР не найден

Это допустимый результат, не ошибка модуля. В отчёт пишется «не найдено в
открытых источниках» — не пустая строка, не общая фраза о том, что «скорее
всего в компании есть HR-отдел». Домысливать нельзя.

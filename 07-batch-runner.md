# 07 — Batch Runner

**Вход:** путь к `.xlsx` со списком компаний.
**Выход:** markdown-отчёт + черновики по каждой компании, `run-state.json`,
сводная `summary.xlsx`.

## Что делать

1. Прочитай входной файл:

   ```
   python scripts/batch_xlsx_reader.py --file <input.xlsx>
   ```

   Отсутствие необязательных столбцов — предупреждение из самого скрипта,
   не повод останавливать batch (§11 тест-плана build-спеки, пункт 8).

2. Если `run-state.json` уже существует в рабочей директории прогона —
   это возобновление, а не новый прогон. Прочитай его, найди первую строку
   со статусом, отличным от `done`, и продолжи с неё. Не начинай сначала и
   не дублируй уже обработанные строки — п.3.1.2 ТЗ явно требует
   возможности «остановить и позже возобновить».

3. Для каждой необработанной строки:
   - выставь `status: "in_progress"` в `run-state.json`;
   - прогони модули 01→06 по этой строке — **без остановки на вопрос
     пользователю**: модуль 01 теперь всегда разрешает неоднозначность
     компании автоматически (см. `modules/01-company-resolve.md` п.4) и
     при необходимости пишет `needs_review`, а не блокирует прогон;
   - запиши результат: `status: "done"`, `report_path`, `persons_found`,
     `max_confidence`, `industry`, `contacts`, `persons[]` (для сводки),
     `needs_review` (если модуль 01 его выставил — прокинь как есть,
     `build_summary_xlsx.py` сам отрисует колонку и подсветку);
   - при сбое источника по одной компании — **не останавливай весь
     прогон**. Зафиксируй `status: "failed"`, `error: "<причина>"` для этой
     строки и переходи к следующей. «Данные не найдены» по отдельному полю
     — тоже не повод помечать всю строку как failed, только конкретное
     поле остаётся пустым с пометкой.

4. Формат `run-state.json` — см. пример в build-спеке §8 (07-batch-runner):
   `{"input_file", "started_at", "rows": [{"idx", "company", "status",
   "report_path", "persons_found", "max_confidence"}, ...]}`. Сохраняй
   после каждой строки, не только в конце прогона — иначе прерывание
   посреди batch обнуляет прогресс, что напрямую противоречит цели
   чекпоинта.

5. По завершении (или по явному запросу пользователя посреди прогона):

   ```
   python scripts/build_summary_xlsx.py --state run-state.json --out summary.xlsx
   ```

   После этого — и только после этого, не раньше — стоит одним сообщением
   перечислить пользователю компании с непустой колонкой «Требует
   проверки» (если такие есть), со ссылкой на их отчёты. Это единственная
   точка во всём batch-прогоне, где неоднозначности компании доходят до
   пользователя — не по одной по ходу обработки.

## Производительность

Реалистичная скорость последовательного прогона — порядка 5–15 компаний в
час (упирается в вежливые задержки между запросами к одному домену и в
отсутствие параллельных воркеров в этой среде). Целевые 200–300
компаний/час из ТЗ требуют отдельной инфраструктуры (см. SKILL.md, «Что
остаётся за пределами скилла») — не пытайся достичь этой скорости
параллельным запуском нескольких инстансов модулей в рамках одного чата,
это не даст ожидаемого ускорения и усложнит чекпоинт.

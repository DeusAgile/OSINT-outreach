# TalentMind Outreach Intelligence

Пайплайн research → отчёт → черновики outreach для одной компании или
batch-списка из `.xlsx`. Реализует компонент Enrichment/LLM Service и
частично Data Collection Service из ТЗ «TalentMind Outreach Intelligence»
(разделы 6–8 ТЗ — веб-интерфейс, БД, очередь задач, SLA — вне объёма этого
скилла, это отдельная разработка веб-сервиса поверх пайплайна).

**LinkedIn не реализуется** — рынок посреднических API схлопнулся (Proxycurl
закрыт после иска LinkedIn, январь–июль 2025), прямой скрапинг нарушает ToS,
и для российского рынка связка hh.ru + media_search + реестры юрлиц решает
ту же задачу лучше.

## Архитектурный принцип

Модули пайплайна (`modules/01-*.md` … `modules/07-*.md`) не привязаны к
конкретным источникам. Каждый модуль отвечает за стадию обработки и
получает список источников своей категории из `config/sources.md` **при
каждом запуске**, а не хранит его внутри себя. Добавление источника — одна
строка в `sources.md`, без правки логики модулей.

Скрипты в `scripts/` инкапсулируют работу с источниками и отдают модулям
единообразный JSON-конверт (см. `scripts/common.py`, функция `envelope()`).
Модуль не знает и не должен знать, получен ли результат через API, парсинг
HTML или headless-браузер — только `ok`, `data`, `warnings`, при неудаче
`error`.

## Как запускать пайплайн

1. Для одной компании: прогони модули по порядку —
   `01-company-resolve` → `02-company-data-collect` → `03-lpr-search` →
   `04-digital-footprint` → `05-report-builder` → `06-outreach-drafts`.
   Прочитай соответствующий `modules/0N-*.md` перед каждым шагом — не
   полагайся на память о том, что он делает, файлы могли быть
   отредактированы пользователем.

2. Для batch-списка компаний из `.xlsx`: используй `07-batch-runner.md`,
   который сам вызывает 01–06 по каждой строке с чекпоинтом.

3. Перед первым запуском в новой рабочей директории: скопируй
   `config/config.example.json` в `config/config.json` (см.
   `config/README.md` — там же инструкция получения токена hh.ru,
   опционального).

## Единый конверт ответа скриптов

Каждый скрипт в `scripts/` печатает в stdout строго JSON:

```json
{
  "ok": true,
  "source": "hh.ru",
  "method": "html_data_qa",
  "fetched_at": "2026-09-01T10:12:00Z",
  "url": "https://hh.ru/employer/4334427",
  "data": {},
  "warnings": ["<чего не удалось получить>"]
}
```

При неудаче — `"ok": false` и `"error": {"type": "...", "message": "..."}`.
**Скрипт никогда не падает молча и никогда не зависает на долгие ретраи** —
недоступность источника это `ok: false` с причиной в stderr/warnings, а не
исключение или бесконечное ожидание. Читай `warnings` даже при `ok: true` —
частичный успех (например, hh.ru отдал название и сайт, но не отдал
вакансии) обычное дело, не ошибка.

## Anti-patterns

**Прочитай `anti-patterns.md` перед сборкой отчёта, не только перед его
финальной проверкой.** Ключевое: не приписывать факт человеку по слабому
совпадению имени, не выдавать TENTATIVE за CONFIRMED, не восполнять
недостающие данные домыслом, не переносить в черновик факты, которых нет в
отчёте. `scripts/entity_resolve.py` кодирует часть этих правил как
детерминированную логику — используй его вывод как есть в модуле 03, не
переоценивай confidence вручную.

## Экономия токенов

Измерено на реальном прогоне (webpractik.ru, 4 страницы), не оценено на
глаз: **`site_crawler.py` — единственный по-настоящему дорогой источник**,
26.7 КБ JSON на один сайт при старом дефолте (4000 символов текста на
страницу без очистки от навигации/подвала). Это ≈6-7 тыс. токенов с одного
источника на одну компанию — при batch на 20+ компаний счёт идёт на сотни
тысяч токенов только на этот шаг. Остальные источники (hh.ru ≈2 КБ,
media_search ≈5 КБ) на порядок дешевле и трогать их не требовалось.

Что уже сделано в скрипте, менять не нужно:
- Все скрипты печатают компактный JSON (`common.py: emit()`, без
  отступов) — раньше был `indent=2` для удобства чтения человеком в
  момент разработки, а его читает модель в проде. Измерено: на плоских
  ответах (`hh_client.py`) это ≈24% меньше байт при абсолютно той же
  информации — отступы никогда не несли смысла для JSON-парсера. На
  сильно вложенных (`site_crawler.py` с текстом страниц) эффект меньше
  (≈6%), потому что там доминирует сам текст, а не структура — но это
  тоже чистая экономия без потерь, не компромисс.
- `dreamjob_client.py` режет текст каждого отзыва на 400 символов по
  умолчанию (`--max-chars-per-review`) — тот же принцип, что и у
  `site_crawler.py`: с 15 отзывами без среза счёт может уйти за 8-9 КБ на
  один такой вызов.
- `site_crawler.py` режет текст страницы на 1500 символов
  (`--max-chars-per-page`, можно увеличить для конкретной компании при
  необходимости) и убирает `<nav>/<header>/<footer>/<script>/<style>`
  перед подсчётом — эти блоки идентичны на каждой странице сайта и раньше
  вытесняли содержательный текст из среза. Извлечение ФИО/контактов
  (`extract_people`/`extract_contacts`) работает по полному очищенному
  тексту ДО среза — точность извлечения не страдает, экономия только на
  объёме, который уходит в контекст модели. Полный HTML всегда остаётся в
  `cache/` — если понадобится больше текста конкретной страницы, читай
  оттуда точечно, не поднимай лимит для всего прогона.
- `modules/03-lpr-search.md`: `web_search` вызывается по эскалации (если
  `media_search.py` вернул пусто/слабо), не параллельно с
  `media_search.py` на каждой компании — иначе поиск удваивается там, где
  DuckDuckGo и так справился.

Что стоит соблюдать по ходу работы, а не в самих скриптах:
- **В batch-режиме (`modules/07-batch-runner.md`) не вставляй полный
  markdown отчёта/черновиков в чат построчно** — только статус и путь к
  файлу, сводка — в конце через `build_summary_xlsx.py`. На 20+ компаниях
  это крупнее, чем все вызовы скриптов вместе взятые.
- Для batch снижай `--limit` у `media_search.py`/`web_search` относительно
  ручного режима на одну компанию (например 15-20 вместо 30) — полнота
  поиска на компанию менее критична, когда компаний много, а стоимость
  запроса линейно умножается на их число.
- Не перечитывай уже полученный JSON от скрипта повторно ради удобства —
  `entity_resolve.py`/`build_summary_xlsx.py` читают файлы (`candidates.json`,
  `run-state.json`) напрямую, не через повторную вставку в контекст.

## Где экономия токенов не должна экономить на качестве

**Пропуск обязательных шагов ради бюджета — не экономия, а другой вид
ошибки, и он уже реально произошёл.** На кейсе WMX модуль 03 в одном из
прогонов не разобрал найденную ростер-страницу setka.ru через
`--single-page` — сама возможность работала (проверено), просто шаг не
довели до конца, и HR-контакт (Даниил Рыжов), который лежал там открытым
текстом, не попал в отчёт. Нет доказательств, что это было именно
экономией токенов, а не случайностью — но это именно то, к чему приводит
любая логика вида «пропустить необязательный на вид шаг, если бюджет
поджимает». Обязательные шаги (single-page разбор найденных ростер-
страниц, cross-check через `web_search` при `match_type: partial` в
модуле 01, entity_resolve.py перед выводом персон) не сокращаются ради
экономии — экономить нужно на объёме данных, которые уходят в контекст
на каждом шаге (см. выше), не на количестве шагов.

**Сделано** (это было предложено выше как «ещё не сделано», а теперь
построено): `scripts/collect_company.py` — оркестратор, объединяющий
модуль 02 и этап 1 модуля 03 (hh.ru + сайт + habr + широкий поиск
руководства + разбор найденных ростер-страниц) в один вызов с одним
JSON-ответом вместо 5-7 отдельных. Не новая логика — вызывает
существующие функции (`hh_client`/`site_crawler`/`habr_client`/
`media_search`) напрямую как Python-импорты, не subprocess, с общей
сессией/кэшем на все источники. Побочный, но важный эффект: разбор
ростер-страниц теперь встроен в код, а не в инструкцию, которую модель
обязана не забыть выполнить — прямая реакция на реальный пропуск этого
шага на кейсе WMX (см. `modules/03-lpr-search.md`). Проверено живьём на
Вебпрактике: нашёл «Алина Нагабедян — Менеджер по персоналу», которого не
находили несколько ручных прогонов подряд ранее в тот же день.

При сборке заодно нашёлся и починен реальный баг в `site_crawler.py`:
`_robots_allows()` молча трактовал HTTP 403 НА САМ robots.txt (отказ в
доступе к файлу, часто общая анти-бот защита сайта — не «Disallow»
внутри его содержимого) как «обход полностью запрещён», из-за чего
wmx.pro не обходился вообще. Теперь такой случай — «не удалось
проверить, обход разрешён по умолчанию» с явным warning, а не тихий
отказ.

## Проверенное окружение (важно для интерпретации сбоев)

Проверено фактическим запуском в среде исполнения скилла — не домыслы, а
результат живых тестов:

| Что | Результат |
|---|---|
| `hh.ru/employer/{id}` HTML | Работает, `[data-qa]`-селекторы актуальны |
| `api.hh.ru` без токена | 403 (`bad_user_agent: blacklisted`, ddos-guard) — блокировка IP дата-центра, не баг. `hh_client.py` автоматически уходит на HTML-fallback (и для `--employer-id`/`--url`, и для `--search`) |
| `hh_client.py --search` без действительного токена | Тоже 403 на `api.hh.ru/employers`, тоже молча уходит на fallback — но fallback здесь не парсинг страницы компании, а поиск среди открытых вакансий (`hh.ru/search/vacancy`), поэтому находит только компании с активными вакансиями прямо сейчас. Для компании без вакансий — `media_search.py` (см. `modules/01-company-resolve.md`) |
| `t.me/s/<channel>` | Работает стабильно, публичная лента, ~20 постов за запрос |
| `career.habr.com`, `tenchat.ru` | Работают |
| `dreamjob.ru` — карточка работодателя и `/interviews` | Работает, SSR, все нужные поля (рейтинг, отзывы, описание процесса отбора) вытаскиваются без headless |
| `amlive.ru`, `comnews.ru`, `setka.ru` | Сетевой доступ подтверждён (200 OK); используются через `media_search.py`, не отдельными клиентами, кроме setka.ru (`site_crawler.py --single-page`) |
| `vk.com` | **Заблокирован на уровне сети песочницы Claude** (`x-block-reason: hostname_blocked`) — не анти-бот VK, а блокировка платформы выполнения. `vk_client.py` написан, но не проверен живым запросом — см. предупреждение в самом скрипте |
| Headless-браузер (Chromium) | Может быть доступен или недоступен в зависимости от среды — `tenchat_client.py --headless` сам проверяет через `browser_available()` и не роняет прогон при недоступности |
| **DuckDuckGo/Bing HTML-поиск** (`media_search.py`) | **Ненадёжно** — отдают анти-бот заглушки/decoy-контент с IP дата-центра (та же причина, что и 403 у api.hh.ru). Скрипт не зависает и не падает (короткий таймаут, без долгих ретраев на уровне поиска), но пустой результат **не означает** отсутствие цифрового следа — см. `config/sources.md` |

Если модуль 03/04 получает пустой результат от `media_search.py` — это
сигнал перепроверить вручную или запустить с другого IP, а не факт «у
персоны нет публичной активности».

## Правовые требования (152-ФЗ)

Пайплайн собирает и обрабатывает персональные данные граждан РФ (ФИО,
должность, контакты, публичная активность) для коммерческого аутрича —
область 152-ФЗ: нужны основание обработки, уведомление регулятора, срок
хранения, процедура удаления по требованию субъекта. Скилл этого не
покрывает — хранилища персональных данных между сессиями нет (файловая
система сбрасывается). Presidio для разметки/маскирования ПДн — на этапе
полноценного приложения, не в объёме скилла. Это фиксация риска, не
юридическое заключение — требует подтверждения юристом заказчика перед
продакшн-использованием на реальных персональных данных.

## Что остаётся за пределами скилла

Требует отдельной инфраструктуры (ВМ-сервисы), не решается правкой скилла:

- персистентный кэш между запусками (файловая система сбрасывается между
  сессиями);
- ротация IP/прокси — причина 403 на `api.hh.ru` и ненадёжности
  `media_search.py`, на объёмах блокировки станут систематическими;
- производительность batch — 200–300 компаний/час из ТЗ требует
  параллельных воркеров, последовательный прогон в чате даёт 5–15/час;
- Telegram через MTProto — полная история, поиск по постам, поиск канала
  по имени человека (текущий `tg_channel.py` — только публичная веб-превью);
- транскрипции YouTube/подкастов, реестры юрлиц (Checko/Datanewton) —
  платные API;
- хранение отчётов и удаление ПДн по требованию (152-ФЗ п.8.4) — требует БД.
